Agent Tools & Interoperability

Without agreed-upon open standards, every integration is a custom machine — fragile wrappers, one-off maintenance, a ceiling on ambition. Two protocols change that math: MCP connects agents to tools, and A2A connects agents to each other.

Kanchana Patlolla · Łukasz Olejniczak · Pier Paolo IppolitoGoogle · June 2026
Read the whitepaper on Kaggle →

Tools are what separate an AI agent from a chatbot. A chatbot generates text; an agent acts — it searches the web, runs code, reads a database, sends an email. The model is the brain; tools are the hands. Without them, even the most capable foundation model is a voice in a glass jar. This whitepaper is about what happens when you standardise how agents connect to those tools — and to each other.

01The standard-of-one problem

The pre-standard world of AI tool integration looks exactly like the pre-USB world of computer peripherals: every device had its own connector, and every connector needed its own cable. In AI agent development, each external API required a bespoke wrapper — custom code to translate between the agent's expectations and the API's interface. Multiply that by every tool, every update, every new agent framework, and you get the compounding burden the authors call the standard-of-one problem.

"Without agreed-upon open standards, developers are creating tech debt. Each API is a standard-of-one — low-leverage tasks, fragile bespoke wrappers, maintained forever."

These aren't just annoying to write; they're a ceiling. A developer wrangling custom wrappers is a builder. A developer working with standardised protocols is an orchestrator — free to think at the level of goals, not glue code. That shift — from builder to orchestrator — is the paper's real promise.

02MCP: the USB-C moment for agents

The Model Context Protocol (MCP), introduced in late 2024, is the open standard for connecting tools to foundation models. The framing the authors use is deliberately mundane: MCP is the USB-C of AI. One plug, any device, any machine. MCP works the same way — define a tool in MCP's format once, and it becomes available to any MCP-compatible agent, regardless of vendor or framework.

The architecture is straightforward. An MCP server exposes tools, resources, and prompts. An MCP client (your agent or IDE) discovers and calls them. The server handles authentication, rate limiting, and the translation layer. Your agent just sees: a list of available tools with typed inputs and outputs. No custom wrappers. No maintenance tax. No "which format does this API expect again?"

03A2A: when agents talk to agents

MCP solves the tool problem. But as systems grow more complex, the next bottleneck emerges: how do agents coordinate with each other? The answer is A2A (Agent-to-Agent protocol) — an open standard that lets agents delegate subtasks, share state, and collaborate across organisational or vendor boundaries without either side needing to know the other's internal implementation.

The practical implication is significant. Instead of building one monolithic agent that tries to do everything, you can compose a team: an orchestrator agent that understands the goal, a research agent that has deep web access, a code agent specialised in a particular language, a QA agent that runs evals. Each does what it's best at. A2A is the protocol that lets them hand off work to one another cleanly. The whitepaper's headline claim is that with MCP + A2A together, a vibe coder can assemble a virtual data and execution team in a single afternoon — without writing any glue code.

04From builder to orchestrator

The conceptual shift this paper argues for is worth pausing on. In a world without open standards, the developer is a builder: they write adapters, maintain integrations, and spend cognitive budget on the plumbing. With MCP and A2A, the plumbing is standardised — the developer becomes an orchestrator, working at the level of goals, team composition, and quality gates.

"Adopting these layers allows for a shift from being a mere builder to a high-level orchestrator."

This mirrors the broader arc of the Vibe Coding series: as each layer of friction is standardised away, the effective leverage point for human judgment moves higher. You don't eliminate complexity — you compose it rather than hand-code it. The whitepaper calls this the path from "isolated custom machines" to "modular, interoperable platforms."

05Security and enterprise readiness

Open protocols that connect agents to high-value systems are also new attack surfaces. The paper is direct about the risks: MCP servers run with whatever permissions they're granted, prompt injection through tool responses is a real vector, and enterprise environments — with access to production databases, email, and internal APIs — raise the stakes considerably. Trust boundaries matter. In a multi-agent system, a compromised sub-agent can influence the orchestrator. The advice is practical: treat MCP servers as you would any third-party dependency — audit them, scope their permissions, and apply the same zero-trust assumptions you would to an external API.

06The practical payoff

The promise of the paper isn't abstract. The authors frame it concretely: in a single afternoon, a developer using MCP and A2A can assemble a virtual team that searches the web, queries a database, executes code, sends a summary email, and hands off results between specialist agents — all without custom integration code. The maintenance tax drops to near zero, because the standard handles versioning and compatibility. The ceiling on what one developer can build rises dramatically.

This is the Day 2 lesson of the Vibe Coding series: Day 1 taught you what an agent is. Day 2 teaches you what an agent can do — by connecting it, via open standards, to everything that exists beyond its context window. (Day 3 asks: how do you give that agent portable, reusable knowledge?)
